## Главный критерий качества offline analysis

**Обязательный принцип** (заменяет любые старые приоритеты, которые ему противоречат):

> **Ground truth — основной источник оценки качества клиентских миссий
> offline analysis, в первую очередь миссий, где действительно была покупка.**

Что это значит на практике:

- Offline analysis должен восстанавливать **реальные клиентские миссии** из сырой
  транскрипции. Ключевая задача — найти миссию, в которой была реальная покупка,
  и правильно определить её границы.
- **Количество найденных dialog-сегментов — НЕ метрика качества.** Не считать
  результат хорошим только потому, что coverage=100%, unassigned=0, нет дублей,
  «разумное» число диалогов, XLSX/PDF создаются успешно.
  *Техническая валидность отчёта ≠ качество анализа.*
- Главный признак успеха — **соответствие реальным продажам** (recall реальных
  покупок + отсутствие ложных + корректное is_sale).
- Сопоставление с GT **не должно** опираться на `client_id`; `client_id` —
  только debug/нумерация, источник истины НЕ является.
- Признаки сопоставления: `store_id` + время + содержание транскрипции +
  логические границы клиентской миссии + факт покупки.

**Явный приоритет (ранжирование):**
`GROUND TRUTH RECALL > количество найденных диалогов > попытки угадать
сомнительные диалоги`. Реальные покупки из GT — **пропускать нельзя**.

- **Сомнительное лучше пропустить, чем придумать:** если система не уверена,
  что дополнительный диалог — настоящая клиентская миссия, **не определять**
  его как `customer dialog`. Не гнаться за максимумом диалогов и не считать
  хорошим результатом большое количество найденных миссий.
- **Длинный сегмент ≠ одна миссия:** внутри одного длинного сегмента могут быть
  несколько реальных клиентских миссий/покупок; главная опасность —
  потерять отдельную реальную покупку внутри него (не «спрятать» в одном диалоге).
- **GT проверяет и segmentation, и classification:** не только `is_sale`, но и
  «правильно ли выделена миссия / не объединены ли несколько клиентов».

### GT-регрессия (правило)

Перед **каждым** существенным изменением segmentation/classification/prompt/thresholds:
1. Проверить результат на доступных ground-truth данных (начиная с `reports/Документы продаж за 27.08.2026г.xlsx`).
2. Смотреть **прежде всего**:
   - сколько реальных продаж найдено (recall);
   - сколько пропущено (NOT_FOUND);
   - сколько ложных совпадений (false-positive buy);
   - правильно ли выделены клиентские миссии;
   - правильно ли определён `is_sale`;
   - не объединены ли несколько реальных клиентов в один сегмент.
3. Не оптимизировать систему только под количество диалогов.

### Будущие GT-файлы

Первый эталон — `reports/Документы продаж за 27.08.2026г.xlsx`.
В системе ожидается появление **множества** аналогичных GT-выгрузок за другие
даты/магазины. Документация и код рассматривают GT как **постоянный канал
проверки качества**, а не разовый эксперимент по конкретной дате. GT по мере
появления используется для regression testing и оценки новых версий
prompt/segmentation/classification.

## Ключевые правила для работы (обязательно)

1. **Не изменять исходный код проекта и raw-отчёты** без явной задачи.
2. При любых пересчётах final-отчётов:
   - бэкап старого final в `reports_root_backup/` **до** перезаписи;
   - raw `transcript_report_*.xlsx` — только чтение;
   - XLSX и PDF строятся из одних и тех же `final_rows`;
   - PDF: без session_ids / client_id / raw JSON / CoT.
3. Sales ground truth (`sales_gt.py`, `--sales-ground-truth`) — **только отдельный режим**;
   без флага production-поведение не меняется.
4. LLM-конфиг (production): model `qwen3.8:27b`, host `http://172.18.0.1:11434`,
   num_ctx **131072**, num_predict **128000**, workers **1**, retries **2**, confidence_min **0.6**
   (значения в `CURRENT_STATUS.md`; кодом задаются `OFFLINE_NUM_CTX`/`OFFLINE_NUM_PREDICT`/`taxonomy.py`).
5. Не создавать дубликаты документации: новое состояние — в `CURRENT_STATUS.md`/`TODO.md`.

## Быстрые команды

```bash
# offline pipeline (одна дата) — по текущей конфигурации:
python3 offline_analysis/run.py   # --input reports/transcript_report_YYYY-MM-DD.xlsx

# backfill ВСЕХ дат (последовательный, 1 worker, ошибки не останавливают batch):
python3 offline_analysis/batch_run.py

# эксперимент sales ground truth (08-27):
python3 offline_analysis/run.py --sales-ground-truth "reports/Документы продаж за 27.08.2026г.xlsx"

# валидация:
python3 scripts/validate_finals.py
python3 scripts/validate_pdfs.py
python3 scripts/summary.py
```

## Конвейер offline

```
run.py → segmentation (LLM) → re-split (LLM, по умолчанию on) → classification (LLM)
       → build_final_rows → XLSX + PDF + *debug.json
```

`client_id` из realtime-контура **НЕ является источником истины** для сегментации —
только debug/нумерация, назначается ПОСЛЕ сегментации. Логика выделяет реальные
логические customer dialogs (несколько клиентов/покупок должны стать разными диалогами).
