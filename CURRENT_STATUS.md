## Главный критерий качества (обязательно)

> **Ground truth — основной источник оценки качества клиентских миссий
> offline analysis, в первую очередь миссий, где была реальная покупка.**

Полная формулировка + правила GT-регрессии + позиция по будущим GT-файлам —
в **`AGENTS.md`** (раздел «Главный критерий качества offline analysis»). Коротко:

- Главное — **восстановить реальные клиентские миссии** и их границы; особенно —
  миссии с фактической покупкой.
- **Количество диалогов ≠ качество.** coverage/unassigned/дубли/«разумное» число
  диалогов/успешный XLSX+PDF — это только *техническая валидность*, не качество.
- **Приоритет:** `GT RECALL > кол-во диалогов > попытки угадать сомнительные`;
  сомнительный dialog лучше **не** помечать как customer — но **реальные покупки
  из GT пропускать нельзя** (детали — `AGENTS.md`).
- Сопоставление с GT **не по `client_id`** (он — только debug/нумерация), а по:
  `store_id` + время + содержание транскрипции + логические границы миссии + факт покупки.
- Долгий сегмент (десятки/сотни минут) **НЕ считается автоматически одной миссией** —
  внутри могут быть несколько клиентов/покупок/посещений; главная опасность —
  **потеря отдельной реальной покупки внутри длинного сегмента**.
- GT используется **и для оценки classification, и для проверки качества segmentation**
  (правильно ли выделена миссия / не объединены ли несколько клиентов).
- GT — **постоянный канал проверки качества** (ждём множество GT-файлов за разные
  даты/магазины), а не разовый эксперимент по одной дате.

## Что сейчас работает

- **Realtime-контур (production)**: microphone → VAD → S3/MinIO → Kafka/Redpanda → ASR → PostgreSQL → classification/alerts → reports. Стабилен, описан в `docs/*`.
- **Offline pipeline (активная зона разработки)**:
  `offline_analysis/run.py` → segmentation (LLM) → re-split длинных диалогов (LLM) → classification (LLM) → `build_final_rows` → **XLSX + PDF** (из одних и тех же `final_rows`).
  - PDF делает **0** LLM-вызовов; из `final_rows` + lookup реплик.
  - PDF **не содержит** session_ids, client_id, raw JSON; `model_reasoning` — только короткий безопасный бизнес-текст (CoT/длинные рассуждения отбрасываются, см. `pdf_report.py`).
- **Batch-режим**: `offline_analysis/batch_run.py` — пересчёт всех `reports/transcript_report_YYYY-MM-DD.xlsx` (включая **2026-08-27** и **2026-08-28**), последовательно (1 worker), ошибка одного дня не останавливает batch, raw-файлы не трогает, старые final-файлы бэкапятся (бэкап: `reports_root_backup/`).
- **Эксперимент sales ground truth**: `offline_analysis/sales_gt.py`, включается только флагом `--sales-ground-truth <xlsx>` (без флага production-поведение не меняется).

## Архитектура (кратко)

```
Realtime:  microphone → VAD (Triton online_vad) → S3/MinIO → Kafka/Redpanda
           → ASR (Triton EMformer) → PostgreSQL → classification + alerts → reports

Offline:   offline_analysis/run.py
           → segmentation (LLM, client_id realtime НЕ используется как источник истины —
             только debug/нумерация, назначается ПОСЛЕ сегментации)
           → re-split длинных dialog-сегментов (LLM, включён по умолчанию; --no-resplit отключает)
           → classification (LLM) → build_final_rows
           → XLSX + PDF (одни final_rows) + *debug.json
```

Ограничения сегментации: выделяться должны **реальные логические customer dialogs**.
Только технический `target_chunk_tokens` — лимиты контекста LLM; `--gap-sec/--max-sec` удалены как жёсткие правила.

## Известные проблемы

1. **Смешение нескольких клиентов в одном длинном диалоге (главный P0-риск).** Подтверждено на 2026-09-04:
   - **08-27 client_3 (27.9 мин, buy/True)**: 3 независимых «добрый день» внутри одного финального
     диалога → 2–3 разных клиента не разделены (re-split не сработал). Прямой симтом потери отдельных
     покупок / неверных границ миссии.
   - **08-25 client_11 (23.4 мин)**: 2 приветствия → вероятно 2 клиента.
   - 08-29 (58.7 мин), 08-28 (34 мин), 09-03 (42.3 мин) — очень длинные (попадают в `kept_single`/
     `re_long` candidates) — «долгий ≠ одна миссия». **Решение: не hard-cut по 60 мин, а LLM-review
     по признакам** (новое приветствие, завершение оплаты + новая встреча, смена `seller_id`, паузы).
2. LLM-nondeterminism: при пересчёте одной даты количество диалогов может отличаться на ±1 (09-01: 17 vs 18).
3. Деградация segmentation (пустой ответ LLM → одиночные `unknown`-сегменты): 08-25: 885, 08-27: 1117,
   08-28: 2374, 08-30: 1275, 08-29: 1067 — покрытие строк полное (lost=0), но структура деградировала.
4. **`coverage.ok:false` на 08-25..08-30, 09-02/09-03 — ЛОЖНЫЙ сарегон (P1-bug, корневая причина найдена).**
   `run.py:422-423` сравнивает union per-store индексов сегментов с общим `total_input_rows`, но
   `start_index` — **per-store** (каждый магазин от 0, `segmentation.py:182-191`). У дат с >1 магазином
   union < total → `ok=False`, **при полностью валидном реальном покрытии**
   (`sum(s.row_count) == total_input_rows` на всех 9 дат проверено). На 09-01 (1 магазин) `ok=True`.
   **Правка:** `coverage_ok = sum(row_count)==total` (не менять индексы). Детали и план —
   `SESSION_CHECKPOINT.md` §2.4/§3.4.
5. Файлы 09-03/08-31 в `reports/` owned by `root` (внутри контейнера пишут как root) — при перезаписи
   учитывать ownership/permissions (host-пользователь `developer` может не писать в root-owned файлы).
6. Sales GT: 39/80 продаж NOT_FOUND — часть покупок вовсе не выделены как dialogs (сегментация), часть — wrong type.
